### TK6 re-verification, 2026-07-27 — wider than recorded

Planning 003 turned up three defects the original TK6 entry did not have. Recorded
here because the audit docs still describe TK6 as a four-item finding.

- **New, in `tikhonov.h`**: the example declares `TikhonovResult *result` twice in
  one scope (`:101` and `:105`) — a redefinition error independent of the missing
  `grid_info`. And the compile line (`:122`) omits `grid_analysis.c`, which the
  corrected example needs; without it the link fails.
- **New, in `savgol.h` — outside TK6 entirely**: `:73` and `:79` call
  `analyze_grid(x, 6, 0)` with three arguments. The real signature takes two
  (`grid_analysis.h:36`); `store_spacings` was removed, as `revision.h:98`
  records. Same defect class, different header, never recorded anywhere. Folded
  into 003 so the class is closed at once.
- Worth knowing: `savgol.h:98,101` documents Tikhonov's API **correctly**,
  `grid_info` and all — better than `tikhonov.h` documents its own. The
  cross-reference survived the drift; the module's own example did not.

Nothing prevents this recurring: headers are prose and the compiler never reads
them. 003 verifies by extracting the examples and compiling them, but that is a
one-off gate, not a standing one. If a third example rots, add "grep the headers
when you change a public signature" to the `smooth-dev-tasks` skill.

## Findings considered and rejected

Recorded so nobody re-audits them.

- **TK3 — L-curve corner detection is triply fragile**: dead finding. The L-curve
  method and the `n > 20000` branch that reached it were deleted in `tikhonov.c`
  V5.4 (2026-07-26). `doc/audit-tikhonov.md` should be updated to retire it.
- **TK7 — redundant solves in the auto-lambda path**: measured, not worth doing.
  On 100k points, `-m 2 -l auto` takes 0.465 s versus 0.210 s for `-l 0.1` — about
  0.25 s of redundant work, much of the baseline being I/O. Its first bullet (the
  `n > 20000` GCV+L-curve double solve) is dead along with TK3.
- **TK4 — exact GCV trace**: a Hutchinson estimator or band-factorisation diagonal
  is a large intervention justified only if auto-lambda precision is a real
  constraint. Nothing currently depends on it.
- **`polyfit.c:244` — `sing_vals[effective_rank - 1]`**: verified safe. The
  Vandermonde matrix always has an all-ones column (x is strictly increasing), so
  `s[0] > 0` and `rank >= 1`; the index can never be `-1`.
- **Security**: no findings. Offline CLI with no network, shell execution, or
  credentials. The bounds handling in `parser.c` was re-read: `MAX_LINE`
  truncation detection, `MAX_COLS` overflow detection on both branches, and
  `strtod` + `endptr` + `isnan`/`isinf` validation all hold.
- **Performance**: no findings worth acting on. Whole-program timings are
  dominated by I/O at realistic sizes.
- **B3 — untracked scratch files in the working tree**: real but a one-line
  `.gitignore` edit; a plan would cost more than the fix.
